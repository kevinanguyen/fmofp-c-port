## Development Status Disclaimer

**⚠️ NOT FOR OPERATIONAL FLIGHT USE.** FMOFP is a training system. Its aircraft, sensors and threats are
simulated; its flight software is written to the rules of avionics code (no dynamic memory after start-up, no
exceptions, every value carrying its validity) so that interns learn on code that looks like the real thing, but it
has not been certified and must not be used to fly anything.

### Current status (2026-11-22)

- **The C++ port is complete.** Every unit of the conversion plan is done or deliberately struck (the HUD, which
  was an empty placeholder). The flight logic is C++17 in 18 partitions; the displays, the plant, the scenario
  engine, the prompt and the recorder are Python; the bus controller is C++.
- **The ported logic is measured against the frozen Python** by oracle tests: the same inputs into the frozen
  Python and the C++, the same outputs required. Where the port departs from the Python (a defect that made a
  function unusable, or new behaviour), the departure is recorded with its evidence in `B20SS/icd/README.md`,
  section 2.
- **Known limitations** are listed in the ICD README's section 12 (the backlog) and in chapter 13: among them, the
  flight surfaces terminal's control laws are reversed (not in the aircraft's loop), the MFD's holographic weather
  page is not fed, the plant's random walk is the default aircraft for the tests.

## Third-Party Components and Standards

- **C++:** GCC (MSYS2 UCRT64 on Windows), CMake, Ninja, GoogleTest, cppcheck, clang-tidy, gcovr.
- **Python:** Python 3.10+, PyQt6 (the displays), NumPy and SciPy (the plant and the oracle tests), SQLite (the data
  recorder), qasync, click.
- **Standards:** MIL-STD-1553B (the bus's word formats, command/response protocol and mode codes, simulated over
  UDP); the C++ follows a MISRA-style subset checked by clang-tidy.
